# 1. Angular Fundamentals — Questions 1–30

## 1. What is Angular?

**Answer:**  
Angular is a **TypeScript-based open-source frontend framework** developed by Google for building web applications, especially **Single Page Applications (SPAs)**.

Angular provides built-in features such as:

- Components
    
- Templates
    
- Routing
    
- Dependency Injection
    
- Forms
    
- HTTP communication
    
- Directives
    
- Pipes
    
- RxJS/Observables
    
- Change detection
    
- Testing support
    

### Example

```typescript
@Component({
  selector: 'app-user',
  template: `<h1>Hello {{ name }}</h1>`
})
export class UserComponent {
  name = 'Ashok';
}
```

Here, Angular combines the **TypeScript class** with an **HTML template** to create UI.

### Interview point

> Angular is a complete frontend framework, whereas libraries such as React primarily focus on the UI layer.

# 3. Difference between AngularJS and Angular?

|AngularJS|Angular|
|---|---|
|Version 1.x|Angular 2+|
|JavaScript primarily|TypeScript primarily|
|Controller-based|Component-based|
|`$scope`|No `$scope`|
|Older digest cycle|Modern change detection|
|MVC-style|Component architecture|
|Less optimized|Better optimization|
|NgModules commonly used|Standalone components are preferred in modern Angular|
|Older architecture|Ivy-based architecture|

### Simple example

AngularJS:

```javascript
$scope.name = "Ashok";
```

Angular:

```typescript
name = "Ashok";
```

Template:

```html
<h1>{{ name }}</h1>
```

### Interview answer

> AngularJS is the original 1.x framework, while Angular refers to the modern Angular platform starting from Angular 2. Modern Angular uses TypeScript, components, modern compilation, dependency injection, and standalone APIs.

# 4. What is a Single Page Application (SPA)?

A **Single Page Application** loads the main HTML page once and dynamically changes the displayed content without completely reloading the browser page.

### Traditional application

```text
Home → Server → New HTML
About → Server → New HTML
Contact → Server → New HTML
```

### SPA

```text
Browser
   |
   +---- Angular Application
             |
             +-- Home
             +-- About
             +-- Contact
```

Angular Router changes the displayed component.

Example:

```typescript
const routes: Routes = [
  { path: 'home', component: HomeComponent },
  { path: 'users', component: UsersComponent }
];
```

When navigating from `/home` to `/users`, Angular can change the component without a full page reload.

# 5. What is TypeScript?

TypeScript is a **superset of JavaScript** developed by Microsoft.

It adds features such as:

- Static typing
    
- Interfaces
    
- Generics
    
- Enums
    
- Access modifiers
    
- Better tooling
    
- Compile-time checking
    

Example:

```typescript
let age: number = 39;
let name: string = "Ashok";
```

JavaScript:

```javascript
let age = 39;
```

TypeScript:

```typescript
let age: number = 39;
```

TypeScript is ultimately compiled/transpiled to JavaScript that browsers can execute.

Angular uses TypeScript because it provides:

### 2. Better IDE support

You get:

- Autocomplete
    
- Navigation

### 3. Object-oriented programming

```typescript

```

### 4. Better maintainability

This is especially useful for large enterprise applications.

### Interview answer

> Angular uses TypeScript because static typing, interfaces, decorators, tooling and object-oriented features make large applications easier to develop, maintain and refactor.

# 21. What are standalone components?

Standalone components are components that **do not need to belong to an NgModule**.

```typescript
  selector: 'app-user',

  template: `<h1>User</h1>`

```

Modern Angular makes standalone components a first-class application architecture.

# 24. What is Ahead-of-Time (AOT) compilation?

AOT means **Ahead-of-Time compilation**.

Angular compiles templates and Angular code **during the build process before the application is sent to the browser**.

Conceptually:

```text
Angular Source
     ↓
Build
     ↓
Angular Compiler
     ↓
Optimized JavaScript
     ↓
Browser
```

### Benefits

- Faster startup
    
- Smaller runtime work
    
- Template errors detected during build
    
- Better optimization
    
- Production builds are optimized
    

AOT is the standard approach for production Angular builds.

---

# 25. What is Just-in-Time (JIT) compilation?

JIT means **Just-in-Time compilation**.

Angular compilation happens at runtime rather than entirely during the build.

Conceptually:

```text
Application
    ↓
Browser
    ↓
Angular compiler
    ↓
Application execution
```

JIT can be useful during development scenarios, although modern Angular development/build workflows rely heavily on AOT.

---

# 26. Difference between AOT and JIT?

|AOT|JIT|
|---|---|
|Compile before runtime|Compile at runtime|
|Build-time compilation|Runtime compilation|
|Better production startup|More runtime compilation work|
|Errors detected earlier|Some errors can appear at runtime|
|Standard for production|Historically useful in development|

### Interview answer

> AOT compiles Angular templates during the build process, whereas JIT compiles them at runtime. AOT is preferred for production because it improves startup, optimization and security characteristics.

# 27. What is tree shaking?

Tree shaking is a build optimization technique that removes **unused code** from the final JavaScript bundles.

Suppose:

```typescript
import { UserService } from './user.service';
```

But another large piece of code is never used.

The build system can eliminate unused portions where possible.

Conceptually:

```text
Source Code
   |
   +-- Used code ───────> Bundle
   |
   +-- Unused code ─────> Removed
```

Result:

> Smaller bundles → less JavaScript → faster loading.

# 28. What is Angular Ivy?

**Ivy** is Angular's modern rendering and compilation architecture.

It replaced the older **View Engine** architecture starting with Angular 9.

Ivy improved:

- Compilation
    
- Rendering
    
- Debugging
    
- Bundle optimization
    
- Incremental compilation
    
- Tree shaking

# 29. Benefits of Ivy?

Important benefits:

### Smaller bundles

Better tree shaking can remove unused code.

### Faster compilation

# 60. Smart vs Presentational Components

This is a **very important architecture/interview question**.

## Smart Component

A smart component is responsible mainly for:

- Business/application logic
    
- Getting data
    
- Calling services
    
- Managing state
    
- Handling user actions
    
- Passing data to child components
    

It is sometimes called a **Container Component**.

## Presentational Component

A presentational component is mainly responsible for:

- Displaying UI
    
- Receiving data
    
- Raising UI events
    
- Being reusable
    
- Avoiding business logic where practical
    

It is also called a **Dumb/UI Component**.

---

## Example

Imagine a user management screen.

### Smart component

```typescript
@Component({
  selector: 'app-user-page',
  template: `
    <app-user-list
      [users]="users"
      (deleteUser)="deleteUser($event)">
    </app-user-list>
  `
})
export class UserPageComponent {

  users: User[] = [];

  constructor(private userService: UserService) {}

  ngOnInit() {
    this.userService.getUsers()
      .subscribe(users => {
        this.users = users;
      });
  }

  deleteUser(id: number) {
    this.userService.deleteUser(id)
      .subscribe(() => {
        this.users = this.users.filter(x => x.id !== id);
      });
  }
}
```

This component:

```text
UserPageComponent
       |
       +-- Calls API/service
       +-- Owns state
       +-- Handles business/application logic
       +-- Passes data to child
```

Therefore it is a **Smart/Container component**.

---

## Presentational component

```typescript
@Component({
  selector: 'app-user-list',
  template: `
    <div *ngFor="let user of users">
      {{ user.name }}

      <button (click)="deleteUser.emit(user.id)">
        Delete
      </button>
    </div>
  `
})
export class UserListComponent {

  @Input()
  users: User[] = [];

  @Output()
  deleteUser = new EventEmitter<number>();
}
```

This component doesn't call the API.

It receives:

```text
users
```

and emits:

```text
deleteUser
```

Therefore it is a **Presentational component**.


### Important

`ElementRef` should be used carefully.

For DOM manipulation, prefer Angular APIs such as:

```text
Renderer2
Angular bindings
HostBinding
HostListener
```

where appropriate.

---

# 72. What are the risks of using `ElementRef`?

Direct DOM manipulation can introduce several problems.

### 1. Security risk

Unsafe values inserted into the DOM can potentially create XSS vulnerabilities.

### 2. Server-side rendering issues

Code that assumes `window` or `document` exists may fail in SSR/non-browser environments.

### 3. Reduced portability

You become tightly coupled to the browser DOM.

### 4. Harder testing

Direct DOM manipulation can make components/directives harder to test.

Instead of:

```typescript
this.el.nativeElement.style.color = 'red';
```

prefer:

```typescript
this.renderer.setStyle(
  this.el.nativeElement,
  'color',
  'red'
);
```

Or, where appropriate, use template bindings.

---

# 73. What is `HostListener`?

`@HostListener` listens to events on the element hosting the directive/component.

Example:

```typescript
@HostListener('mouseenter')
onMouseEnter() {
  console.log('Mouse entered');
}
```

Usage:

```html
<p appHighlight>
  Hover me
</p>
```

The directive listens to the host `<p>` element.

You can access the event:

```typescript
@HostListener('click', ['$event'])
onClick(event: MouseEvent) {
  console.log(event);
}
```

---

# 74. What is `HostBinding`?

`@HostBinding` binds a directive/component property to a property, attribute, class, or style of its host element.

Example:

```typescript
@HostBinding('class.active')
isActive = false;
```

When:

```typescript
isActive = true;
```

Angular adds:

```html
class="active"
```

to the host element.

Another example:

```typescript
@HostBinding('attr.aria-label')
label = 'User';
```

### Modern Angular

You may also use host metadata:

```typescript
@Directive({
  selector: '[appHighlight]',
  host: {
    '[class.active]': 'isActive',
    '(click)': 'onClick()'
  }
})
```

---

# 75. What are standalone directives?

A standalone directive does not need to be declared in an NgModule.

Example:

```typescript
@Directive({
  selector: '[appHighlight]',
  standalone: true
})
export class HighlightDirective {}
```

It can then be imported directly where needed.

For example:

```typescript
@Component({
  imports: [HighlightDirective],
  template: `
    <p appHighlight>Hello</p>
  `
})
export class AppComponent {}
```

### Advantage

Dependencies become more explicit and the architecture becomes simpler.

---

# 76. What are control-flow blocks (`@if`, `@for`)?

Modern Angular provides built-in template control-flow syntax.

### `@if`

```html
@if (isLoggedIn) {
  <p>Welcome</p>
} @else {
  <p>Please login</p>
}
```

### `@for`

```html
@for (user of users; track user.id) {
  <p>{{ user.name }}</p>
}
```

### `@switch`

```html
@switch (role) {
  @case ('admin') {
    <p>Admin</p>
  }
  @case ('user') {
    <p>User</p>
  }
  @default {
    <p>Guest</p>
  }
}
```

These are built into Angular's template syntax rather than being custom structural directives you have to import.

---

# 77. Why were control-flow blocks introduced?

The new control-flow syntax was introduced to improve Angular templates.

Advantages include:

### 1. Cleaner syntax

Compare:

```html
<div *ngIf="isLoggedIn">
```

with:

```html
@if (isLoggedIn) {
```

### 2. Better type checking

The syntax provides Angular with more explicit template control-flow semantics.

### 3. Better developer experience

It resembles familiar programming-language control flow.

### 4. Built-in functionality

You don't need to import `NgIf`/`NgFor` merely to use the built-in control-flow syntax.

### 5. Better iteration support

`@for` provides explicit tracking:

```html
@for (user of users; track user.id) {
```

---

# 78. Difference between `*ngIf` and `@if`?

|`*ngIf`|`@if`|
|---|---|
|Traditional structural directive|Modern built-in control flow|
|Uses `*` syntax|Uses block syntax|
|Directive-based|Built-in template control flow|
|Common in older codebases|Preferred for new Angular code|
|Can require directive import in standalone setup|Built into Angular template syntax|

Example:

### Old

```html
<div *ngIf="isAdmin">
  Admin
</div>
```

### Modern

```html
@if (isAdmin) {
  <div>
    Admin
  </div>
}
```

---

# 79. Difference between `*ngFor` and `@for`?

Traditional:

```html
<div *ngFor="let user of users">
  {{ user.name }}
</div>
```

Modern:

```html
@for (user of users; track user.id) {
  <div>{{ user.name }}</div>
}
```

### Major advantage

`@for` requires an explicit tracking expression.

```html
track user.id
```

This helps Angular identify which items correspond to which DOM nodes when the collection changes.

### Interview answer

> `@for` is the modern built-in control-flow syntax and provides explicit tracking semantics, while `*ngFor` is the older structural-directive approach.

---

# 80. When should you prefer control-flow blocks?

For **new Angular applications**, prefer:

```text
@if
@for
@switch
```

unless there is a specific reason to use the older directive syntax.

For existing applications:

```text
*ngIf
*ngFor
*ngSwitch
```

may still be present and are perfectly understandable.

### Practical recommendation

```html
@if (users.length > 0) {
  @for (user of users; track user.id) {
    <div>{{ user.name }}</div>
  }
} @else {
  <p>No users found.</p>
}
```

This is generally cleaner than deeply nested structural-directive syntax.

# 4. Services & Dependency Injection — Questions 81–110

# 81. What is a service?

A service is a TypeScript class used to encapsulate **reusable application logic or data-access logic**.

Example:

```typescript
@Injectable({
  providedIn: 'root'
})
export class UserService {

  getUsers() {
    // API call
  }
}
```

A component can consume it:

```typescript
constructor(private userService: UserService) {}
```

### Typical services

```text
UserService
AuthService
PaymentService
LoggingService
NotificationService
ConfigurationService
```

---

# 82. Why use services?

Services help separate responsibilities.

Without service:

```text
Component
 ├── UI
 ├── API calls
 ├── business logic
 ├── authentication
 └── logging
```

This becomes difficult to maintain.

With services:

```text
Component
   |
   +── UserService
   +── AuthService
   +── NotificationService
```

### Benefits

- Reusability
    
- Separation of concerns
    
- Testability
    
- Centralized business logic
    
- Easier maintenance
    

---

# 83. What is Dependency Injection?

**Dependency Injection (DI)** is a design pattern where an object receives the dependencies it needs instead of creating them itself.

Bad approach:

```typescript
class UserComponent {

  userService = new UserService();

}
```

Better:

```typescript
constructor(
  private userService: UserService
) {}
```

Angular creates/provides the dependency.

### Concept

```text
Component
    ↓
Requests UserService
    ↓
Angular Injector
    ↓
Creates/returns UserService
```

---

# 84. Benefits of Dependency Injection?

### 1. Loose coupling

Component doesn't need to know how service is created.

### 2. Testability

You can provide a mock service.

### 3. Reusability

The same service can be used in multiple places.

### 4. Lifecycle management

Angular manages provider instances according to their injector scope.

### 5. Configuration

You can replace implementations using providers.

---

# 85. What is a provider?

A **provider** tells Angular's injector **how to create or obtain a dependency**.

Example:

```typescript
providers: [
  UserService
]
```

This essentially tells Angular:

> When someone requests `UserService`, provide an instance of it.

A provider can use:

```text
useClass
useValue
useFactory
useExisting
```

---

# 86. What is `providedIn: 'root'`?

Example:

```typescript
@Injectable({
  providedIn: 'root'
})
export class UserService {}
```

It registers the service with the application's root injector.

Typically, this means:

> One shared instance is available throughout the application.

It also supports tree-shakable service registration.

### Important nuance

`providedIn: 'root'` generally gives application-wide singleton-like behavior **within that Angular application injector**, but it is not a universal singleton across unrelated applications or separate injector hierarchies.

---

# 87. What is the injector hierarchy?

Angular DI uses hierarchical injectors.

Conceptually:

```text
Platform Injector
       ↓
Environment/Application Injector
       ↓
Element/Component Injectors
       ↓
Child Components
```

When Angular needs a dependency, it searches from the requesting context upward through the injector hierarchy according to Angular's DI rules.

### Why is this important?

You can have:

```text
Root UserService
```

and override it for a specific component subtree.

---

# 88. Difference between root and component injectors?

### Root/Application injector

Provides dependencies broadly across the application.

Example:

```typescript
@Injectable({
  providedIn: 'root'
})
```

Typically one instance for that application injector.

### Component injector

Created/configured through a component's `providers`.

Example:

```typescript
@Component({
  providers: [UserService]
})
```

Now that component and its descendants can receive an instance associated with that component injector.

### Important

```text
Root provider
   ↓
Shared application instance

Component provider
   ↓
Scoped instance for component subtree
```

---

# 89. What are injection tokens?

An injection token is an identifier Angular's DI system uses to look up a dependency.

Classes themselves can be DI tokens:

```typescript
UserService
```

But sometimes you need to inject something that isn't a class, such as:

```text
string
configuration object
interface
primitive value
```

For those cases, use an `InjectionToken`.

---

# 90. What is `InjectionToken`?

`InjectionToken<T>` creates a strongly typed token for DI.

Example:

```typescript
export const API_URL =
  new InjectionToken<string>('API_URL');
```

Provider:

```typescript
providers: [
  {
    provide: API_URL,
    useValue: 'https://api.example.com'
  }
]
```

Inject:

```typescript
constructor(
  @Inject(API_URL) private apiUrl: string
) {}
```

Modern Angular can also use:

```typescript
const API_URL =
  new InjectionToken<string>('API_URL');
```

with `inject(API_URL)`.

### Why?

Interfaces disappear at runtime, so Angular cannot use:

```typescript
interface Config {}
```

directly as a runtime DI token.

---

# 91. What is the `inject()` function?

`inject()` allows you to obtain a dependency from Angular's DI system without using constructor parameters.

Example:

```typescript
private userService = inject(UserService);
```

Then:

```typescript
users = this.userService.getUsers();
```

It is commonly used in:

- Components
    
- Services
    
- Directives
    
- Guards
    
- Interceptors
    
- Functions executed in an injection context
    

Example:

```typescript
@Injectable({
  providedIn: 'root'
})
export class UserService {

  private http = inject(HttpClient);

}
```

---

# 92. Constructor injection vs `inject()`?

### Constructor injection

```typescript
constructor(
  private userService: UserService
) {}
```

### `inject()`

```typescript
private userService = inject(UserService);
```

### Constructor injection advantages

- Very explicit dependencies
    
- Familiar
    
- Easy to understand
    
- Works naturally with classes
    

### `inject()` advantages

- Useful outside constructors
    
- Convenient for functional APIs
    
- Useful in guards/interceptors/providers
    
- Can reduce constructor boilerplate
    

### Interview answer

> Both use Angular's DI system. Constructor injection expresses dependencies through the constructor, while `inject()` retrieves dependencies from an active injection context and is particularly useful with functional Angular APIs.

---

# 93. What is a factory provider?

A factory provider creates a dependency using a function.

Example:

```typescript
{
  provide: API_URL,
  useFactory: () => {
    return 'https://api.example.com';
  }
}
```

Factory providers are useful when the value depends on:

- Configuration
    
- Other services
    
- Environment
    
- Runtime conditions
    

Example:

```typescript
{
  provide: API_URL,
  useFactory: (config: AppConfig) =>
    config.production
      ? 'https://api.com'
      : 'https://dev-api.com',
  deps: [AppConfig]
}
```

---

# 94. What is a value provider?

A value provider supplies a fixed value.

Example:

```typescript
{
  provide: API_URL,
  useValue: 'https://api.example.com'
}
```

Useful for:

```text
Configuration
Constants
Feature flags
Test values
Environment-specific values
```

Example:

```typescript
export const APP_NAME =
  new InjectionToken<string>('APP_NAME');
```

```typescript
{
  provide: APP_NAME,
  useValue: 'Vehicle Management'
}
```

---

# 95. What is a class provider?

A class provider tells Angular which class should be instantiated for a token.

Example:

```typescript
{
  provide: UserService,
  useClass: UserService
}
```

More interesting example:

```typescript
{
  provide: Logger,
  useClass: ProductionLogger
}
```

Now whenever Angular asks for:

```typescript
Logger
```

it creates:

```text
ProductionLogger
```

This is useful for substituting implementations.

---

# 96. What is an existing provider?

`useExisting` creates an **alias** to an existing provider rather than creating another instance.

Example:

```typescript
{
  provide: Logger,
  useExisting: ProductionLogger
}
```

If:

```typescript
ProductionLogger
```

already has an instance in the injector, requesting `Logger` resolves to that same instance.

### Important distinction

```text
useClass
   ↓
Can create a separate instance

useExisting
   ↓
Alias to existing instance
```

This distinction is a favorite senior-level DI interview question.

---

# 97. What are multi-providers?

A multi-provider allows **multiple values/providers to be associated with the same token**.

Example concept:

```typescript
{
  provide: SOME_TOKEN,
  useClass: FirstHandler,
  multi: true
},
{
  provide: SOME_TOKEN,
  useClass: SecondHandler,
  multi: true
}
```

Injecting the token gives:

```text
[
  FirstHandler,
  SecondHandler
]
```

### Where useful?

- Plugin architectures
    
- Multiple handlers
    
- Interceptor-style systems
    
- Extensible configuration
    

Angular itself uses multi-provider patterns in several APIs.

---

# 98. How do you create singleton services?

The common approach is:

```typescript
@Injectable({
  providedIn: 'root'
})
export class AuthService {}
```

This makes the service available from the root injector and typically gives one shared instance within the application.

### Alternative

Register it once at the application/root level:

```typescript
providers: [
  AuthService
]
```

### Avoid

Providing the same service in a component:

```typescript
@Component({
  providers: [AuthService]
})
```

if you specifically need application-wide shared state, because that creates a scoped provider and can result in different instances.

---

# 99. What is the service lifetime in Angular?

A service's lifetime depends on **where its provider is registered**.

### Root/application provider

Usually lives for the lifetime of the Angular application.

### Component provider

Lives while that component's injector/subtree exists.

Conceptually:

```text
Application starts
      ↓
Root Service created when first requested
      ↓
Application running
      ↓
Application destroyed
      ↓
Root service destroyed
```

Component-scoped:

```text
Component created
      ↓
Service created when requested
      ↓
Component destroyed
      ↓
Service becomes eligible for destruction
```

---

# 100. What is a shared service?

A shared service is a service used by multiple components to share logic or state.

Example:

```typescript
@Injectable({
  providedIn: 'root'
})
export class CartService {

  cartCount = signal(0);

  addItem() {
    this.cartCount.update(count => count + 1);
  }
}
```

Multiple components can inject:

```typescript
private cartService = inject(CartService);
```

and access the shared state.

---

# 101. How do services communicate between components?

Suppose:

```text
Component A
Component B
```

They are unrelated.

A shared service can hold state:

```typescript
@Injectable({
  providedIn: 'root'
})
export class MessageService {

  message = signal('');
}
```

Component A:

```typescript
service.message.set('Hello');
```

Component B:

```typescript
service.message()
```

Other options include:

- RxJS `Subject`
    
- `BehaviorSubject`
    
- Signals
    
- Signal-based stores
    
- State management libraries
    

### Architecture

```text
Component A
     ↓
Shared Service
     ↓
Component B
```

# 102. What is state sharing?

State sharing means making application data available to multiple components.

Example:

```text
User information
Shopping cart
Authentication state
Selected vehicle
Theme
Notifications
```

Instead of:

```text
Component A owns user
Component B separately owns user
Component C separately owns user
```

you can centralize shared state:

```text
             Shared State
            /      |      \
           ↓       ↓       ↓
       Component A B     C
```

Modern Angular applications can use **signals** for lightweight shared state.

# 103. What are environment providers?

Environment providers allow providers to be configured for an **application/environment injector** rather than tied to a particular component.

They are heavily used with standalone Angular APIs.

Example:

```typescript
bootstrapApplication(AppComponent, {
  providers: [
    provideHttpClient()
  ]
});
```

`provideHttpClient()` returns providers suitable for the application environment.

Another example:

```typescript
export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),

```

### Concept

```text
Environment Providers
        ↓

        ↓
Standalone Angular application
```

# 104. What is `ApplicationConfig`?

`ApplicationConfig` represents application-level configuration for a standalone Angular application.

Example:

```typescript
export const appConfig: ApplicationConfig = {
```

# 106. What are platform injectors?

The **platform injector** is above the application-level injector.

It provides dependencies that can be shared at the Angular platform level.

Conceptually:

```text
Platform Injector
       ↓
Application Injector
       ↓
Component Injector
```

This becomes particularly relevant when understanding:

- Multiple Angular applications
    
- Angular platform-level services
    
- Advanced DI architecture
    

### Interview point

Most normal business services should not be registered at the platform level. Application/root providers are generally the appropriate scope.

# 107. What are optional dependencies?

Sometimes a dependency may or may not be available.

You can tell Angular:

> If this dependency doesn't exist, give me `null` instead of throwing an error.

Using `inject()`:

```typescript
const logger =
  inject(LoggerService, { optional: true });
```

Then:

```typescript
if (logger) {
  logger.log('Hello');
}
```

This is useful for dependencies that are not guaranteed to be provided.

---

# 108. What is `@Optional()`?

`@Optional()` tells Angular that a dependency is optional.

Example:

```typescript
constructor(
  @Optional()
  private logger: LoggerService | null
) {}
```

If Angular cannot find `LoggerService`, it provides `null` instead of throwing a DI error.

### Modern equivalent

With `inject()`:

```typescript
private logger =
  inject(LoggerService, { optional: true });
```

---

# 109. What is `@Self()`?

`@Self()` tells Angular:

> Look for this dependency only in the current injector.

Example:

```typescript
constructor(
  @Self() private service: MyService
) {}
```

Angular does **not continue searching parent injectors**.

### Concept

Normal:

```text
Current Injector
      ↓
Parent Injector
      ↓
Root Injector
```

`@Self()`:

```text
Current Injector only
```

If the provider isn't there, Angular throws a DI error unless the dependency is also optional.

---

# 110. What is `@SkipSelf()`?

`@SkipSelf()` tells Angular:

> Don't use the current injector; start searching from the parent injector.

Example:

```typescript
constructor(
  @SkipSelf()
  private service: MyService
) {}
```

This is useful when a component has its own provider but you specifically want the parent's instance.

### Concept

Without `@SkipSelf()`:

```text
Current → Parent → Root
```

With `@SkipSelf()`:

```text
Current X
   ↓
Parent → Root
```

# 5. Angular Forms — Questions 111–140

## 111. What are Angular Forms?

Angular Forms provide APIs for **collecting, validating, tracking, and submitting user input**.

Angular has two major approaches:

```text
Angular Forms
     |
     ├── Template-driven Forms
     |
     └── Reactive Forms
```

Example:

```html
<input [(ngModel)]="userName">
```

or Reactive Forms:

```typescript
name = new FormControl('');
```

Forms can manage:

- Input values
    
- Validation
    
- Errors
    
- Touched/dirty state
    
- Submission
    
- Dynamic controls
    
- Complex nested forms
    

---

# 112. Template-driven vs Reactive Forms

|Template-driven|Reactive|
|---|---|
|Form logic mainly in template|Form model mainly in TypeScript|
|Uses `FormsModule`|Uses `ReactiveFormsModule`|
|`[(ngModel)]` commonly used|`FormControl`, `FormGroup`, `FormArray`|
|Easier for simple forms|Better for complex forms|
|Less explicit|More explicit|
|Validation often in HTML|Validation defined in TypeScript|
|Harder to scale for complex forms|Better enterprise scalability|

### Template-driven

```html
<input
  name="email"
  [(ngModel)]="email"
  required
  email>
```

# 123. What is cross-field validation?

Cross-field validation validates **multiple fields together**.

Example:

```text
Password
Confirm Password
```

Individual validation isn't enough.

You need:

```text
password === confirmPassword
```

Example:

```typescript
function passwordMatch(
  group: AbstractControl
): ValidationErrors | null {

  const password = group.get('password')?.value;
  const confirm = group.get('confirmPassword')?.value;

  return password === confirm
    ? null
    : { passwordMismatch: true };
}
```

Apply it to the `FormGroup`.

```typescript
form = this.fb.group(
  {
    password: [''],
    confirmPassword: ['']
  },
  {
    validators: passwordMatch
  }
);
```

# 137. How do you build custom form controls?

Implement `ControlValueAccessor`.

The key methods are:

```typescript
writeValue(value: any): void
registerOnChange(fn: any): void
registerOnTouched(fn: any): void
setDisabledState?(isDisabled: boolean): void
```

Conceptually:

```text
Angular Form
     |
     | writeValue()
     ↓
Custom Control
     |
     | onChange(value)
     ↓
Angular Form
```

Example simplified control:

```typescript
export class CustomInput
  implements ControlValueAccessor {

  value = '';

  private onChange = (value: string) => {};
  private onTouched = () => {};

  writeValue(value: string): void {
    this.value = value ?? '';
  }

  registerOnChange(fn: (value: string) => void): void {
    this.onChange = fn;
  }

  registerOnTouched(fn: () => void): void {
    this.onTouched = fn;
  }

  setDisabledState(isDisabled: boolean): void {
    // update UI
  }

  updateValue(value: string) {
    this.value = value;
    this.onChange(value);
  }
}
```

## 171. What is RxJS?

**RxJS (Reactive Extensions for JavaScript)** is a library for reactive programming using **Observables**.

Angular uses RxJS extensively for:

```typescript
  console.log(value);
});
```

```text
2
3
```

### Interview answer

> RxJS is a reactive programming library based on Observables. It provides operators to compose, transform, combine, filter, and handle asynchronous data streams.

# 172. What is an Observable?

An **Observable** represents a stream of values over time.

It can emit:

```text

1
2
3
...
```

or:

```text

HTTP response
HTTP response
```

An Observable can emit:

- zero values
    
- one value
    
- many values
    
- an error
    
- completion
    

### Example

# 176. What is Subject?

A **Subject** is both:

2. Observer
    

Therefore you can:

# 177. What is BehaviorSubject?

`BehaviorSubject` is a Subject that:

- requires an initial value
    
- stores the latest value
    
- immediately gives the latest value to a new subscriber
    

```typescript
const userSubject =
  new BehaviorSubject<string>('Guest');

userSubject.next('Ashok');

userSubject.subscribe(user => {
  console.log(user);
});
```

Output:

```text
Ashok
```

### Typical state service

```typescript
private userSubject =
  new BehaviorSubject<User | null>(null);

user$ = this.userSubject.asObservable();

  this.userSubject.next(user);
}
```

# 178. What is ReplaySubject?

`ReplaySubject` stores previous emissions and replays them to new subscribers.

```typescript
const subject = new ReplaySubject<number>(2);

subject.next(1);
subject.next(2);
subject.next(3);

subject.subscribe(value => {
  console.log(value);
});
```

Output:

```text
2
3
```

Because it was configured to replay the last **2 values**.

### Use cases

- caching recent events
    
- event history
    
- sharing previous emissions

# 179. What is AsyncSubject?

`AsyncSubject` emits **only the last value**, and only when the Observable completes.

```typescript
const subject = new AsyncSubject<number>();

subject.subscribe(value => {
  console.log(value);
});

subject.next(10);
subject.next(20);
subject.next(30);

subject.complete();
```

Output:

```text
30
```

### Difference

```text
Subject        → every value
BehaviorSubject → latest value + initial value
ReplaySubject   → previous values
AsyncSubject    → final value after completion
```

# 180. Hot vs Cold Observables

## Cold Observable

Each subscriber gets its own execution.

```text
Subscriber A → Execution A
Subscriber B → Execution B
```

Example:

```typescript
const observable$ = new Observable(observer => {
  console.log('Executed');
  observer.next(Math.random());
});
```

Every subscription executes the producer again.

---

## Hot Observable

The producer exists independently of subscribers.

```text
             Producer
             /      \
            ↓        ↓
        Subscriber Subscriber
```

Subjects are commonly used for hot/multicast behavior.

### Interview answer

> A cold Observable creates or executes its producer separately for each subscriber, while a hot Observable shares an existing execution among subscribers.

# 183. What is switchMap()?

`switchMap()` maps each source value to an inner Observable and **cancels/unsubscribes from the previous inner Observable** when a new source value arrives.

Example:

```typescript

  .pipe(

      this.http.get(`/api/users?search=${term}`)
    )
  )
  .subscribe(users => {
    this.users = users;
  });
```

Suppose the user types:

```text
A
An
Ash
Asho
Ashok
```

`switchMap()` ensures the latest search is the one that matters.

```text
A       ────────X
An          ─────X
Ash             ─────X
Asho                ───X
Ashok                  ───── RESPONSE
```

# 184. What is mergeMap()?

`mergeMap()` subscribes to inner Observables concurrently.

```typescript
  .pipe(

  )
  .subscribe();
```

Conceptually:

```text

ID 2 ─── Response
ID 3 ─────────── Response
```

All requests can execute simultaneously.

### Use when

Order isn't important and concurrency is acceptable.

# 185. What is concatMap()?

`concatMap()` processes inner Observables **sequentially**.

```typescript
actions$
  .pipe(
    concatMap(action =>
      this.http.post('/api/action', action)
    )
  )
  .subscribe();
```

Conceptually:

```text
Request 1 → complete
               ↓
Request 2 → complete
               ↓
Request 3 → complete
```

### Use cases

- ordered API calls
    
- sequential updates
    
- queue processing

# 186. What is exhaustMap()?

`exhaustMap()` ignores new source emissions while the current inner Observable is running.

```typescript
click$
  .pipe(
    exhaustMap(() =>
      this.http.post('/api/payment', {})
    )
  )
  .subscribe();
```

If the user clicks 10 times quickly:

```text
Click 1 → API running
Click 2 → ignored
Click 3 → ignored
Click 4 → ignored
...
API complete
```

### Excellent use case

Preventing duplicate submissions.

# 187. switchMap vs mergeMap vs concatMap vs exhaustMap

This is a **very important interview question**.

|Operator|Behavior|Typical use|
|---|---|---|
|`switchMap`|Cancel previous|Search|
|`mergeMap`|Run concurrently|Independent requests|
|`concatMap`|Queue sequentially|Ordered operations|
|`exhaustMap`|Ignore new while busy|Submit/login/payment|

### Easy memory trick

```text

mergeMap   → all run
concatMap  → one by one
exhaustMap → first wins until complete
```

# 201. What causes memory leaks in RxJS?

A common cause is an Observable subscription that remains active after a component is destroyed.

Example:

```typescript
ngOnInit() {
  this.service.data$.subscribe(data => {
    this.data = data;
  });
}
```

If the stream doesn't complete, the subscription may remain.

### Better

```typescript
this.service.data$
  .pipe(
    takeUntilDestroyed()
  )
  .subscribe(data => {
    this.data = data;
  });
```

Other causes:

- nested subscriptions
    
- long-lived Subjects
    
- event listeners
    
- improper shared streams
    
- subscriptions that are never cleaned up

# 203. What is takeUntil()?

`takeUntil()` completes the source Observable when another Observable emits.

```typescript

}
```

Conceptually:

```text
data$ ────────────────────────
                                X
destroy$ ────────────────●─────
                          ↓
                     subscription
                       completes
```

# 204. What is takeUntilDestroyed()?

`takeUntilDestroyed()` is Angular's modern lifecycle-aware solution for automatically completing subscriptions when the associated Angular context is destroyed.

```typescript
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';

constructor() {
  this.service.data$
    .pipe(
      takeUntilDestroyed()
    )
    .subscribe(data => {
      console.log(data);
    });
}
```

It avoids manually creating:

```typescript
destroy$ = new Subject<void>();
```

### Important

It must be used in an appropriate Angular injection context, or supplied with a `DestroyRef` when used outside the default context.

# 205. What is Async Pipe?

The `async` pipe subscribes to an Observable or Promise in the template and displays its latest value.

```typescript
users$ = this.userService.getUsers();
```

Template:

```html
<div *ngFor="let user of users$ | async">
  {{ user.name }}
</div>
```

Modern control flow:

```html
@for (user of users$ | async; track user.id) {
  <div>{{ user.name }}</div>
}
```

The async pipe also handles subscription cleanup when the view is destroyed.

- automatic subscription
    
- automatic cleanup
    
- less component code
    
- supports reactive programming
    
- works naturally with Angular change detection
    

Instead of:

```typescript
users: User[] = [];
```

you can use:

# RxJS Best Practices

For Question 210, remember these:

### 1. Prefer composition over nested subscriptions

❌

```typescript
a$.subscribe(a => {
  b$.subscribe(b => {
    // nested
  });
});
```

✅

```typescript
a$
  .pipe(
    switchMap(a => b$)
  )
  .subscribe();
```

### 2. Use the correct flattening operator

```text
Latest only     → switchMap
Concurrent      → mergeMap
Sequential      → concatMap
Ignore while busy → exhaustMap
```

### 3. Prefer Async Pipe in templates

```html
{{ user$ | async }}
```

### 4. Clean up long-lived subscriptions

```typescript
takeUntilDestroyed()
```

### 5. Don't abuse Subjects

Use them when you actually need multicasting/state/event pushing.

### 6. Keep streams declarative

Prefer:

```typescript
users$ = search$
  .pipe(
    debounceTime(300),
    distinctUntilChanged(),
    switchMap(search => this.api.search(search))
  );
```

rather than manually managing many variables and subscriptions.

# 8. Angular Signals — 211–230

Signals are one of the most important modern Angular concepts.

## 211. What are Angular Signals?

A **Signal** is a reactive value that Angular can track.

```typescript
count = signal(0);
```

Read it:

```typescript
console.log(this.count());
```

Update it:

```typescript
this.count.set(10);
```

or:

```typescript
this.count.update(value => value + 1);
```

Template:

```html
<p>{{ count() }}</p>
```

Conceptually:

```text
Signal
  ↓
Angular tracks dependency
  ↓
Signal changes
  ↓
Dependent UI updates
```

---

# 212. Why were Signals introduced?

Signals provide a simpler fine-grained reactive primitive for Angular.

They help Angular:

- track dependencies precisely
    
- reduce unnecessary work
    
- simplify local state
    
- reduce reliance on manual subscriptions
    
- improve template reactivity
    
- provide a strong foundation for modern Angular APIs
    

Before Signals, developers frequently used:

```text
Observable
   +
subscribe()
   +
unsubscribe()
```

For simple local UI state, Signals can be much simpler.

---

# 213. What is signal()?

`signal()` creates a writable reactive value.

```typescript
count = signal(0);
```

Read:

```typescript
this.count();
```

Set:

```typescript
this.count.set(5);
```

Update:

```typescript
this.count.update(value => value + 1);
```

Example:

```typescript
increment() {
  this.count.update(value => value + 1);
}
```

---

# 214. What is computed()?

`computed()` creates a **read-only derived Signal**.

```typescript
price = signal(100);
quantity = signal(2);

total = computed(() =>
  this.price() * this.quantity()
);
```

Template:

```html
<p>Total: {{ total() }}</p>
```

If `price` or `quantity` changes, `total` automatically recalculates when needed.

### Concept

```text
price ──────┐
            ↓
         computed
            ↑
quantity ───┘
```

Use `computed()` for **derived state**, not side effects.

---

# 215. What is effect()?

`effect()` runs side-effect logic whenever Signals it reads change.

```typescript
count = signal(0);

constructor() {
  effect(() => {
    console.log('Count:', this.count());
  });
}
```

When:

```typescript
this.count.set(10);
```

the effect reacts.

### Use cases

- logging
    
- localStorage synchronization
    
- analytics
    
- integrating with non-reactive APIs
    

Avoid using effects to represent ordinary derived state. Prefer `computed()` for that.

---

# 216. Writable vs Readonly Signals

### Writable Signal

Can be changed:

```typescript
count = signal(0);

count.set(10);
count.update(x => x + 1);
```

### Readonly Signal

Cannot directly be changed:

```typescript
total = computed(() =>
  this.price() * this.quantity()
);
```

Conceptually:

```text
Writable
  ↓
set()
update()

Readonly
  ↓
read only
```

You can also expose a writable signal through a readonly interface when designing state services.

# 217. Signals vs RxJS

This is another **very important senior-level interview question**.

|Signals|RxJS|
|---|---|
|Reactive state primitive|Reactive stream library|
|Excellent for synchronous state|Excellent for async/event streams|
|Fine-grained dependency tracking|Powerful stream composition|
|`signal()`|`Observable`|
|`computed()`|Operators such as `map()`|
|`effect()`|Side-effect subscription|
|Simple local state|HTTP/WebSocket/events|
|Pull-style reads|Push-based stream model|

### Example

Local UI state:

```typescript
isMenuOpen = signal(false);
```

HTTP search:

```typescript
searchResults$ = searchTerm$
  .pipe(
    debounceTime(300),
    switchMap(term => this.api.search(term))
  );
```

### Best architecture

You don't need to choose only one.

```text
RxJS
 ↓
Async/API/Event processing
 ↓
Signal
 ↓
UI state
```

Angular provides interoperability between Signals and RxJS.

# 218. When should you use Signals?

Use Signals for:

- local component state
    
- derived UI state
    
- synchronous application state
    
- template state
    
- simple shared state
    

Example:

```typescript
isLoading = signal(false);
selectedUser = signal<User | null>(null);
```

Use RxJS for:

- HTTP streams
    
- WebSockets
    
- complex asynchronous workflows
    
- debouncing
    
- cancellation
    
- event streams
    
- sophisticated stream composition

# 219. How do Signals improve performance?

Signals provide **fine-grained dependency tracking**.

Suppose:

```typescript
firstName = signal('Ashok');
lastName = signal('Bhosale');

fullName = computed(() =>
  `${this.firstName()} ${this.lastName()}`
);
```

Angular knows which reactive values the computation depends on.

When:

```typescript
firstName.set('John');
```

the dependent computation/UI can be updated appropriately.

The important idea is:

> Angular can track specific reactive dependencies instead of treating every piece of application state as one undifferentiated change.

# 220. How do Signals work with templates?

Component:

```typescript
count = signal(0);
```

Template:

```html
<h2>{{ count() }}</h2>

<button (click)="count.update(c => c + 1)">
  Increment
</button>
```

Angular tracks that the template reads:

```typescript

```

When the signal changes, Angular knows that the template depends on it.

# 221. What are Signal Inputs?

Signal inputs allow component inputs to be represented as Signals.

Example:

```typescript
import { input } from '@angular/core';

@Component({
  selector: 'app-user',
  template: `
    <h2>{{ name() }}</h2>
  `,
  standalone: true
})
export class UserComponent {

  name = input.required<string>();

}
```

Parent:

```html

```

The child reads:

```typescript
this.name()
```

instead of a traditional mutable input property.

# 222. What are Signal Outputs?

Modern Angular also provides a signal-oriented output API.

```typescript
import { output } from '@angular/core';

export class UserComponent {

  userSelected = output<User>();

  selectUser(user: User) {
    this.userSelected.emit(user);
  }
}
```

Parent:

```html
<app-user
  (userSelected)="onUserSelected($event)"
/>
```

Important distinction:

> Outputs are event emitters represented through Angular's modern output API; they are not simply "Signals that the parent reads."

```typescript
contentChildren()
```

# 224. How do Signals reduce change-detection overhead?

Traditional Angular change detection can involve checking component trees according to Angular's change-detection strategy.

Signals provide dependency information.

For example:

```typescript
name = signal('Ashok');
```

and template:

```html
{{ name() }}
```

Angular knows the template depends on `name`.

When `name` changes, Angular can use that dependency information to identify affected reactive consumers.

### Senior interview answer

> Signals provide fine-grained reactivity and explicit dependency tracking, allowing Angular to perform more targeted reactive updates rather than relying solely on broad change-detection checks.

# 225. Can Signals replace NgRx?

**Not automatically.**

Signals can replace some use cases where NgRx was previously introduced for relatively simple state.

For example:

```text

        ↓
Signals
```

But complex enterprise state may still benefit from NgRx features such as:

- actions
    
- reducers
    
- selectors
    
- effects
    
- centralized state architecture
    
- devtools
    
- predictable event-driven state transitions
    

### Interview answer

> Signals can replace NgRx for some simpler state-management scenarios, but they are not a universal replacement. The choice depends on application complexity and architectural requirements.

# 226. Can Signals coexist with RxJS?

**Yes—and this is a very common modern Angular architecture.**

Angular provides interoperability APIs.

For example:


```text
        ↙       ↘

     ↓

   Signal
     ↓

```

# 227. What is Signal State Management?

Signal state management means using Signals as the reactive source of application state.

Example:

```typescript
@Injectable({
  providedIn: 'root'
})

  private usersState = signal<User[]>([]);

  users = this.usersState.asReadonly();

  addUser(user: User) {
    this.usersState.update(users => [
      ...users,
      user
    ]);
  }
}
```

Component:

```typescript
users = this.userState.users;
```

Template:

```html
@for (user of users(); track user.id) {
  <p>{{ user.name }}</p>
}
```

This is a lightweight state-management approach.

# 228. How do you test Signals?

Signals can be tested directly.

```typescript

  const count = signal(0);

  count.set(10);

  expect(count()).toBe(10);
});
```

Testing `computed()`:

```typescript

  price() * quantity()
);

```

For `effect()`, test the externally observable side effect rather than merely testing that the effect function executed.

# 229. Limitations of Signals

Signals are powerful, but they are not ideal for everything.

### 1. Complex async streams

RxJS is generally better for:

```text
debounce
switchMap
mergeMap
WebSockets
event streams
complex async workflows
```

### 2. Side-effect management

Large applications may need dedicated patterns/libraries rather than many loosely connected effects.

### 3. Learning reactive concepts

Developers still need to understand dependency tracking and reactive state.

### 4. Architecture still matters

Using Signals does not automatically create good state architecture.

You can still create:

```text
too much shared mutable state
circular dependencies
unnecessary effects
```

# 230. Future of Signals in Angular

Signals are a **major direction of modern Angular**.

Angular has progressively expanded Signal-based APIs around:

```text

   ↓
computed()
   ↓

   ↓
Signal Inputs
   ↓
Signal Queries
   ↓

   ↓

```

The important interview point is **not**:

# 237. What are HTTP Interceptors?

An HTTP interceptor is middleware that can inspect or modify HTTP requests and responses.

Concept:

```text
Angular Component
       ↓
    HttpClient
       ↓
   Interceptor
       ↓
     API
       ↓
   Interceptor
       ↓
    Component
```

Example:

```typescript
export const authInterceptor: HttpInterceptorFn =
  (req, next) => {

    const token = 'JWT_TOKEN';

    const clonedRequest = req.clone({
      setHeaders: {
        Authorization: `Bearer ${token}`
      }

    return next(clonedRequest);

```

HTTP requests are immutable, so we generally **clone** the request before modifying it.

# 239. What are Functional Interceptors?

Modern Angular supports **functional interceptors**.

```typescript
import {
  HttpInterceptorFn

  };
```

```typescript
provideHttpClient(
  withInterceptors([
    loggingInterceptor
  ])
)
```

### Why functional interceptors?

They are:

- concise
    
- easier to compose
    
- work naturally with `inject()`
    
- well suited to standalone Angular configuration
    

Example:

```typescript
export const authInterceptor: HttpInterceptorFn =
  (req, next) => {

    const authService = inject(AuthService);

    const token = authService.getToken();

    if (!token) {
      return next(req);
    }

    return next(
      req.clone({
        setHeaders: {
          Authorization: `Bearer ${token}`
        }
      })
    );
  };
```

# 240. How do you handle HttpClient errors?

Use RxJS `catchError()`.

```typescript
getUsers() {
  return this.http.get<User[]>('/api/users')
    .pipe(
      catchError(error => {
        console.error('API Error', error);

        return throwError(
          () => new Error('Unable to load users')
        );
      })
    );
}
```

You can handle common status codes:

```typescript
catchError(error => {

  if (error.status === 401) {
    // Authentication expired
  }

  if (error.status === 403) {
    // Access denied
  }

  if (error.status === 500) {
    // Server error
  }

  return throwError(() => error);
})
```

### Enterprise approach

A common architecture is:

```text
HttpClient
   ↓
Auth Interceptor
   ↓
API
   ↓
Error Interceptor
   ↓
Global Error Service
   ↓
UI notification/logging
```

# 241. What are retry strategies?

Don't blindly retry every error.

A good retry strategy considers:

- HTTP status
    
- network failure
    
- number of attempts
    
- exponential backoff
    
- idempotency
    
- maximum delay
    

Conceptually:

```text
Request
   ↓
Failure
   ↓
Wait 1 sec
   ↓
Retry
   ↓
Failure
   ↓
Wait 2 sec
   ↓
Retry
```

Modern RxJS can implement this with `retry()` and configuration/delay strategies.

For example:

```typescript
retry({
  count: 3,
  delay: 1000
})
```

For production systems, exponential backoff is generally preferable to hammering the API repeatedly.

### Don't retry blindly

Avoid automatic retries for errors such as:

```text
400 Bad Request
401 Unauthorized
403 Forbidden
validation failures
```

# 242. How do you cancel HTTP requests?

Angular HTTP Observables are cancellable through unsubscription.

```typescript
search$
  .pipe(
    switchMap(term =>
      this.http.get(`/api/search?q=${term}`)
    )
  );
```

When a new search term arrives, `switchMap()` unsubscribes from the previous request.

This is excellent for search/autocomplete.

### Manual cancellation

```typescript
const subscription =
  this.http.get('/api/data')
    .subscribe();

subscription.unsubscribe();
```

You can also use `takeUntilDestroyed()` for lifecycle cancellation.

### Senior answer

> Request cancellation is particularly important for rapidly changing UI operations such as search. `switchMap()` is often preferred because it automatically unsubscribes from the previous request when a new value arrives.

# 246. How does JWT Authentication work?

JWT = **JSON Web Token**.

Typical flow:

```text
User
 ↓
Login
 ↓
POST /login
 ↓
Backend validates credentials
 ↓
JWT returned
 ↓
Angular stores/manages token
 ↓
Interceptor adds Bearer token
 ↓
API
```

Request:

```http
Authorization: Bearer eyJ...
```

Interceptor:

```typescript
export const authInterceptor: HttpInterceptorFn =
  (req, next) => {

    const auth = inject(AuthService);
    const token = auth.getToken();

    return next(
      token
        ? req.clone({
            setHeaders: {
              Authorization: `Bearer ${token}`
            }
          })
        : req
    );
  };
```

### Security note

Token storage strategy matters. Avoid casually storing sensitive tokens in `localStorage`; XSS can expose them. A common stronger browser architecture uses secure, appropriately configured cookies for refresh/session credentials.

# 247. What is a Refresh Token Flow?

Access tokens are often short-lived.

Example:

```text
Access Token
    ↓
15 minutes
    ↓
Expires
```

Refresh token/session mechanism is used to obtain a new access token without forcing the user to log in again.

Typical flow:

```text

   ↓
API request
   ↓
401 Unauthorized
   ↓
Refresh endpoint
   ↓
New access token
   ↓
Retry original request
```

### Enterprise complication

If 10 API requests simultaneously receive `401`, you should avoid sending 10 refresh requests.

A robust interceptor coordinates refresh:

```text
Request A ──401─┐
Request B ──401─┤
Request C ──401─┤
                ↓
         One refresh request
                ↓
          New credentials
                ↓
      Retry queued requests
```

This is a common senior Angular interview scenario.

# 248. What is CORS?

**CORS = Cross-Origin Resource Sharing.**

Suppose Angular runs at:




### Important interview point

During development, an Angular dev-server proxy can help avoid development-origin issues:

```text

   ↓
/api
   ↓
Dev Proxy
   ↓
Backend
```

But the production API still needs correct CORS/security configuration when applicable.

## 266. What is Change Detection?

**Change detection** is Angular's mechanism for determining whether the UI needs to be updated when application state changes.

Conceptually:

```text
State changes
     ↓
Angular detects change
     ↓
Checks affected bindings
     ↓
Updates DOM
```

Example:

```typescript
count = 0;

increment() {
  this.count++;
}
```

Template:

```html
<p>{{ count }}</p>
```

When `count` changes, Angular updates the displayed value.

### Interview answer

> Change detection is the Angular process of checking component state and updating the DOM when bound data changes.

# 267. What is the Default Change Detection Strategy?

Angular's default strategy checks components as part of the normal change-detection process.

Example:

```typescript
@Component({
  selector: 'app-user',
  template: `
    <p>{{ user.name }}</p>
  `
})
export class UserComponent {
  user = { name: 'Ashok' };
}
```

With the default strategy, Angular performs broader checks than an `OnPush` component.

### Simplified architecture

```text
Application
    ↓
Root Component
    ↓
Component Tree
    ↓
Angular checks bindings
    ↓
DOM update
```

For large applications, indiscriminate checking can become expensive, which is why `OnPush`, Signals, good component boundaries, and efficient templates are important.

# 268. What is OnPush Change Detection?

`OnPush` tells Angular that a component can use a more optimized change-detection strategy.

```typescript
@Component({
  selector: 'app-user',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <p>{{ user.name }}</p>
  `
})
export class UserComponent {
  @Input() user!: User;
}
```

With `OnPush`, Angular can check the component when relevant reactive/input conditions occur, such as:

- an input reference changes
    
- an event occurs in the component/view
    
- an Observable used through `AsyncPipe` emits
    
- a Signal read by the template changes
    
- the component is explicitly marked for checking
    

### Important problem

Avoid mutating an input object in place:

```typescript
this.user.name = 'John';
```

Prefer creating a new reference:

```typescript
this.user = {
  ...this.user,
  name: 'John'
};
```

### Interview answer

> OnPush reduces unnecessary change detection by allowing Angular to check a component primarily when its inputs or other tracked reactive dependencies change. It encourages immutable data patterns and clearer component boundaries.

# 272. What are TrackBy Functions?

# 279. SSR Performance Considerations

SSR can improve:

- initial HTML availability
    
- perceived loading
    
- SEO for public content
    

But SSR also introduces server-side costs.

Consider:

### 1. Server CPU

Every SSR request may require rendering work.

### 2. API latency

```text
Browser
   ↓
SSR Server
   ↓
Backend API
```

Too many server-side API calls can slow TTFB.

### 3. Caching

Use appropriate caching for public, cacheable content.

### 4. Hydration

The browser must hydrate the server-rendered application.

### 5. Browser/server differences

Code that assumes:

```typescript
window
document
localStorage
```

must be handled carefully in SSR environments.

### Architect answer

> I evaluate SSR not just from a browser perspective but across TTFB, server CPU, API latency, caching, hydration cost, and infrastructure scaling.

# 284. What is Hydration?

Hydration connects Angular behavior to HTML that was already rendered by the server.

Without hydration, the browser could receive HTML and then effectively recreate the UI.

With hydration:

```text
Server
 ↓
HTML
 ↓
Browser
 ↓
Angular reuses existing DOM
 ↓
Event handling/reactivity attached
 ↓
Interactive application
```

### Benefit

It avoids unnecessary destruction and recreation of server-rendered DOM and improves the transition to an interactive application.

# 285. What is Incremental Hydration?

Incremental hydration allows parts of a server-rendered application to become interactive progressively rather than hydrating everything immediately.

Conceptually:

```text

     ↓

     ↓

├─────────────┤

├─────────────┤
│ Analytics   │ → hydrate later
├─────────────┤

└─────────────┘
```

This can reduce the initial hydration workload for large applications.

### Useful for

- large pages

- below-the-fold interactive components
    
- expensive client-side widgets

# 298. How does Angular prevent XSS?

Angular automatically sanitizes certain potentially dangerous values when binding them into security-sensitive contexts.

For example:

```html
<div>
  {{ userInput }}
</div>
```

Angular treats the value as text rather than executable HTML.

Be extremely careful with:

```typescript
innerHTML
```

and especially:

```typescript
bypassSecurityTrustHtml()
```

### Dangerous pattern

```typescript
this.sanitizer
  .bypassSecurityTrustHtml(userInput);
```

Do not use trust-bypass APIs simply to "make HTML work."

Only use them when you fully understand and control the security boundary.

### Other XSS defenses

```text
Angular sanitization
+
CSP
+
output encoding
+
safe DOM APIs
+
input validation
+
secure backend
```

### Important interview answer

> Angular provides contextual sanitization for many template bindings, but it is not a replacement for secure application design. I avoid bypassing sanitization unless the content is trusted and the security implications have been explicitly evaluated.
